TruthLens

AI 생성 콘텐츠 판별 플랫폼

이미지·뉴스·논문을 업로드하거나 URL·텍스트로 입력하면, AI 생성 가능성을 점수와 근거(히트맵·의심 문장·인용 검증)로 보여주는 Flask 웹 서비스.

기간 6인 팀 프로젝트(1주) → 개인 고도화 5일 (2026.07.13–07.17) 스택 Python 3.11 · Flask 3.x GitHub github.com/jjssspark/TruthLens
3min신규 clone → 3개 기능 시연
54→70%backend 테스트 커버리지
31/31테스트 통과, 5일 회귀 없음
11버그 증상→원인→해결 문서화
01 / 09문제 정의

판별 도구 없이, AI 생성물이 범람한다

  • 생성형 AI 기술의 급속한 발전으로 AI 생성 영상·이미지·텍스트(뉴스·논문)가 빠르게 늘고 있음
  • 딥페이크 영상·이미지를 이용한 허위정보 유포
  • AI 생성 가짜뉴스·논문을 통한 여론 조작 및 학술 신뢰성 훼손
  • 일반 사용자가 콘텐츠의 AI 생성 여부를 스스로 판단할 도구가 마땅치 않음
일반 사용자가 콘텐츠의 AI 생성 여부를 판별할 도구가 없다.

팀 프로젝트로 시작된 코드베이스를, 5일간 "기능 추가가 아니라 실제로 동작하고 설명 가능한 상태"로 만드는 데 집중해 개인 포트폴리오로 고도화했습니다.

02 / 09핵심 기능

4개 도메인, 5개 기능 요구사항

기능입력출력상태
FR-01 영상 판별URL / MP4·AVI·MOV·WEBM딥페이크 신뢰 점수, 프레임 의심 구간로드맵 · 스텁
FR-02 이미지 판별JPG·PNG·WebP·GIF (최대 10장)의심 영역 히트맵, EXIF 분석동작
FR-03 뉴스 판별URL / 텍스트(최대 10,000자)출처 신뢰도, 의심 문장 하이라이트동작
FR-04 논문 판별PDF (최대 50MB)인용 교차 검증, 자동 요약동작
FR-05 캐싱·집계 표시동일 콘텐츠 해시재분석 방지, 분석 요청자 수 표시동작

영상 딥페이크 판별은 실제 모델 학습·연동이 5일 스코프에서 비현실적이라 판단, 숨기지 않고 "모델 연동 예정" 배지로 한계를 정직하게 드러내는 쪽을 택했습니다.

03 / 09아키텍처 · 기술 스택

레이어별 스택과 이원화된 캐싱

레이어기술
FrontendHTML5 · CSS3 · JS(Vanilla / Alpine.js)
BackendPython 3.11+ · Flask 3.x
AI 분석Transformers · OpenCV · PyTorch · Gemini · DeepSeek
DatabaseMariaDB 11.x (로컬은 SQLite 폴백)
CacheRedis 7.x
Task QueueCelery + Redis
Web ServerGunicorn + Nginx

캐싱 전략 이원화

분석 비용이 큰 도메인은 Redis, 이력 통계가 필요한 뉴스는 기존 DB 레코드를 재사용합니다.

영상 · 이미지 · 논문→Redis (TTL 24h)
뉴스→DetectionRequest 조회 (TTL 7일)

두 방식이 아직 통일되지 않은 점은 알려진 기술 부채로 남겨두었습니다.

04 / 09기술적 의사결정

스코프를 의도적으로 좁힌다

고민
영상 딥페이크 모델을 5일 안에 학습·연동할지
결정
스텁으로 남기고 "연동 예정" 배지로 명시
이유

Mock이 아닌 실 API로 검증한다

고민
뉴스(Gemini)·논문(DeepSeek) 판별을 목으로 테스트할지
결정

예외 처리를 호출부까지 일관되게 적용한다

고민
모델(detector) 레벨 방어만으로 충분한지

이유

Caching

캐싱을 도메인 특성에 따라 이원화한다

고민
모든 도메인에 Redis 단일 캐시를 쓸지
결정
뉴스는 기존 DB 레코드 조회 방식으로 분리
이유
이력 통계(FR-05)와 캐시 판단을 테이블 조회만으로 동시 처리 가능

고민

이유

05 / 09트러블슈팅 로그

증상 → 원인 → 해결, 12건 중 발췌

DAY 1

PaperDetector 생성자 크래시로 앱 전체가 죽음. API 키 검증을 생성자에서 수행 → 실제 호출 시점(detect())으로 이동, 키가 없어도 서버는 정상 구동(graceful degradation).

DAY 1

평문 비밀번호 저장/비교. werkzeug.security의 generate_password_hash / check_password_hash로 교체.

DAY 2

뉴스/논문 라우트가 서비스 예외를 감싸지 않아 500 HTML 에러 페이지 노출. 라우트에서 ValueError→400, 그 외→500 JSON 응답으로 전면 방어.

DAY 2

DeepSeek 402(잔액 부족) 원본 에러가 그대로 노출. _friendly_error_message()로 402/429/401을 한국어 메시지로 변환, 원본은 서버 로그에만 남김.

DAY 3

320px 모바일에서 결과 게이지가 카드 밖으로 넘칠 뻔함. 페이지 패딩+카드 패딩+고정폭 요소를 직접 산수로 검증 후 width: min(280px, 100%)로 수정.

DAY 4

uploads/에 실제 파일이 커밋 이력에 남아있음. git rm --cached로 추적만 해제, 이후 신규 업로드는 정상적으로 무시됨.

DAY 5

docker compose up이 13일 전 이미지를 재사용해 최신 커밋(로그인 방식 변경, 다크 테마)이 반영되지 않음. 이미지 생성 시각과 git 커밋 시각을 대조해 원인 확정, docker compose up --build로 재빌드하고 실행 안내를 갱신.

전체 12건은 docs/TROUBLESHOOTING.md 참고

07 / 09시연 플로우

키 없이도 죽지 않는 서비스

API 키 유무와 무관하게 각 기능이 독립적으로 실패하도록 설계해, 시연 중 어떤 상태에서도 서버가 응답합니다.

Step 1

이미지 판별

외부 API 키 불필요. 업로드 → 진행률 바 → 신뢰 점수 게이지·히트맵·EXIF 분석까지 즉시 확인 가능해 가장 먼저 보여주기 좋음.

Step 2

뉴스 / 논문 판별

GEMINI_API_KEY / DEEPSEEK_API_KEY 필요. 키가 없어도 에러 없이 200 응답 + "API Key를 확인하세요" 메시지 — Day2 예외 처리가 살아있다는 증거.

Step 3

영상 판별

OpenCV 로컬 휴리스틱으로 프레임을 최대 16장 샘플링해 노이즈·엣지·색상·시간적 일관성을 분석 — 상용 딥러닝 딥페이크 탐지와는 다름을 명시.

백업 자료: docs/assets/truthlens-image-detection-demo.gif (네트워크 장애·쿼터 소진 대비)
08 / 09배포 · 다음 단계

클라우드타입 배포, 그리고 남은 과제

배포 구성

dev→qa→main (자동 배포)

Flask App(Gunicorn) · Celery Worker · MariaDB · Redis를 클라우드타입 프로젝트 내 서비스명으로 상호 통신시키며, GitHub OAuth 연동으로 브랜치 푸시 시 자동 빌드·배포됩니다.

알려진 기술 부채 / 다음 단계

  • 뉴스 캐싱(DB 조회)을 Redis로 통일해 캐시 정책을 한 곳에서 관리
  • 영상 판별(FR-01)에 실제 딥페이크 탐지 모델 연동
  • 테스트 통과 후 배포되는 GitHub Actions 게이트 정식 적용

숨기지 않고 정직하게 한계를 보여주는 것이, 신뢰도 측면에서 더 낫다고 판단했습니다.
