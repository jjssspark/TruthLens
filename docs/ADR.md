# 설계 결정 기록 (ADR)

프로젝트에서 내린 기술 결정 10건입니다. 무엇을 골랐는지보다 그 결정이 실제로 무엇을 바꿨는지에 무게를 뒀습니다.

나중에 뒤집힌 결정은 지우지 않고 "대체됨"으로 표시하고 어느 항목이 대체했는지 적었습니다.
틀린 판단을 지우면 왜 그렇게 판단했는지도 같이 사라집니다.

## ADR-1. 영상 딥페이크 판별 기능 스코프 제외

상태: 대체됨 (ADR-8이 대체)

> 못 하는 걸 숨기는 것보다 드러내는 쪽이 신뢰에 낫다.

배경 · 실제 모델 학습과 연동이 필요해 짧은 기간 안에 구현하는 건 비현실적이라고 봤다.

결정 · 구현하지 않되, "아키텍처는 준비됨, 모델 연동은 로드맵"이라는 사실을 UI 배지로 명시했다.

결과 · 기능을 조용히 빼는 대신 한계를 드러냈다. 미완성을 감추면 나중에 사용자가 직접 발견하게 되고, 그때 잃는 신뢰가 더 크다고 판단했다.

왜 대체됐나 · 이후 실제로 구현했다. 그런데 구현하고 나서 정확도를 재보니 기준선보다 낮았다. "못 해서 안 한다"에서 "해봤는데 안 된다"로 상황이 바뀌었고, 그때의 판단이 ADR-8이다. 드러내는 쪽을 고른다는 원칙 자체는 그대로 이어졌다.

## ADR-2. Mock 대신 실 API로 검증

상태: 유효

> Mock은 성공 경로만 증명한다.

배경 · Mock 테스트는 실제 API의 실패 모드를 드러내지 않는다. 잔액 부족이나 DNS 장애 같은 것들이다.

결정 · 뉴스와 논문 판별을 실제 API 키로 직접 테스트했다.

결과 · DeepSeek 402(잔액 부족)와 네트워크 DNS 장애를 실제로 만나 버그를 찾았고, 예외 처리가 형식이 아니라 실효성이 있는지까지 확인했다.

다만 이 방식에는 대가가 있다. 테스트가 외부 상태에 의존해 조용히 깨진다. 실제로 테스트 하나가 목 없이 Gemini를 호출하고 있었는데, 판별기가 예외를 삼키는 바람에 실패해도 200이 나와 늘 통과했다(트러블슈팅 21번). 지금은 CI에서 키 없이 전체가 통과하도록 경계에서 목으로 막고, 실 API 검증은 손으로 따로 돌린다.

## ADR-3. 에러 처리를 라우트가 아닌 전역 계층에서 보장

상태: 유효

> 한 군데서만 감싸면 감싸지 않은 곳으로 샌다.

배경 · 판별기 레벨에서만 예외를 감싸는 걸로는 부족하다는 걸 500 HTML이 그대로 노출되는 버그로 확인했다.

결정 · `app.py`에 전역 errorhandler를 등록하고, 외부 API 장애는 500이 아니라 502 `ANALYSIS_FAILED`로 구분했다. 알림 기준을 나누기 위해서다.

결과 · 어떤 라우트에서 예외가 새어도 응답에는 에러 코드와 traceId만 나간다. 스택 트레이스는 서버 로그에만 남는다.

## ADR-4. 업로드 경로 path traversal 제거

상태: 유효

> 취약점이 실재했다는 걸 회귀 테스트로 남겼다.

배경 · `file.filename`을 sanitize 없이 `os.path.join`에 넘기고 있어서, 업로드 폴더 바깥에 파일을 쓰는 게 가능했다.

결정 · `backend/services/upload_service.py`의 `save_upload()`로 저장 경로를 일원화하고 `secure_filename` + 확장자 allowlist + uuid 접두어를 적용했다.

결과 · 취약점을 막았고, 겸사겸사 같은 이름 파일이 서로를 덮어쓰던 버그도 함께 해소됐다. 취약점이 실제로 존재했음을 증명하는 회귀 테스트도 남겼다.

## ADR-5. API 응답 규약을 코드가 실제로 지키게 함

상태: 유효

> 문서에만 있는 규약은 규약이 아니다.

배경 · `.claude/standards/api-contract.md`에는 `{success, data, error}`로 적혀 있는데 코드는 `{status, data, meta}`를 반환하고 있었다.

결정 · `backend/api/response.py`의 `ok()`/`fail()`로 전 엔드포인트를 통일하고, 로깅도 구조화 JSON과 traceId 자동 전파로 바꿨다.

결과 · 문서와 코드의 불일치를 없앴다. traceId가 로깅 필터로 전파되니 호출부가 매번 챙기지 않아도 누락이 안 생긴다.

빠뜨린 것 · 봉투를 서버에서 통일했는데 프론트가 그 봉투를 제대로 여는지는 확인하지 않았다. `fail()`이 `data`를 항상 `null`로 두는데 프론트는 `json.data`를 읽고 있어서, 서버가 무슨 말을 하든 화면에는 같은 문구만 떴다(트러블슈팅 20번). 규약을 정했으면 양쪽 끝을 다 봐야 한다.

## ADR-6. 배포 장벽 낮추기

상태: 유효

> 실행이 안 되면 리뷰도 안 된다.

배경 · MariaDB와 Redis 없이는 로컬 실행조차 어려웠다.

결정 · SQLite 폴백을 기본으로 두고, Docker Compose로 `docker compose up` 한 줄이면 뜨게 했다. 필요하면 `--profile full`로 확장한다.

결과 · 새로 clone한 기준으로 3분 안에 실행 가능해졌다.

## ADR-7. 이미지 판별을 3모델 앙상블 중앙값으로

상태: 유효

> 정확도가 같아도 실패 방향이 다르면 합칠 수 있다.

배경 · 단일 모델로 바꾼 뒤에도 다른 생성기로 만든 이미지를 놓쳤다. 사용자가 올린 AI 이미지 5장 중 2~3장만 맞혔다.

후보 5개를 같은 표본(AI 19장 / 진본 16장)으로 비교했더니 셋의 정확도가 똑같은데 실패 방향이 정반대였다.

| 모델 | 정확도 | AI 탐지 | 오탐 |
|---|---|---|---|
| haywoodsloan | 85.7% | 14/19 | 0/16 |
| Organika/sdxl-detector | 85.7% | 19/19 | 5/16 |
| Ateeqq | 85.7% | 19/19 | 5/16 |

기존 모델은 진짜 사진을 한 번도 의심하지 않는 대신 AI를 5장 놓쳤고, 나머지 둘은 AI를 다 잡는 대신 진짜 사진 5장을 의심했다. 오답이 겹치지 않는다는 게 핵심이었다.

결정 · 세 모델 점수의 중앙값을 쓴다. 3개 중 중앙값이 70 이상인 건 "3개 중 2개 이상이 70 이상"과 수학적으로 같아서 곧 다수결이다. 점수 하나만 바꾸면 되니 판정 문구나 신뢰도 계산 같은 하위 로직을 안 건드린다.

- 홀수여야 중앙값이 다수결이 되므로 3개로 묶었다
- 세 호출은 동시에 쏜다. 순차면 대기가 3배다(2.2초 → 0.8초)
- 하나가 실패해도 남은 것들로 판정한다. 전부 실패해야 휴리스틱으로 떨어진다
- 조합 4가지를 다 계산해보고 골랐다. 전원일치는 개선이 없었고, 하나라도는 오탐이 늘어 더 나빠졌다

결과 · 85.7% → 94.3%. 놓치던 5장이 전부 99.9% 이상으로 잡혔다.

받아들인 대가 · 오탐이 0에서 2로 늘었다. 진짜 사진을 AI라고 하는 건 놓치는 것보다 사용자 신뢰에 더 해롭다. 그럼에도 AI를 4장 중 1장씩 놓치는 쪽이 서비스로서 더 문제라고 보고 교체했다. 의도한 트레이드오프다.

## ADR-8. 영상 판별을 재보고 실험적 기능으로 남김

상태: 유효 (ADR-1을 대체)

> 얼마나 안 되는지를 숫자로 알아야 남길지 지울지 고를 수 있다.

배경 · 영상 판별을 구현했는데, 사람이 직접 찍은 영상이 AI 62%로 나왔다. 원인은 얼굴 조작 탐지 모델을 얼굴 없는 화면에 쓰고 있던 것이었다. 이미지 앙상블로 교체해 같은 영상이 15.5%가 됐다.

여기서 끝낼 수도 있었다. 그런데 오탐 하나가 사라졌다고 잘 도는 건 아니라서 공개 데이터셋으로 재봤다.

| 방식 | 정확도 | AI를 AI로 | 진본을 진본으로 |
|---|---|---|---|
| 이미지 앙상블 | 37.0% | 4 / 12 | 6 / 15 |
| 얼굴 조작 탐지 | 37.0% | 9 / 12 | 1 / 15 |
| 픽셀 휴리스틱 | 55.6% | 0 / 12 | 15 / 15 |

기준선은 무조건 "진본"이라고 답하면 55.6%, 동전 던지기가 50%다.

대안도 찾아봤다. 시공간 정보를 쓰는 연구는 활발한데(DeMamba, UNITE, DeCoF) 바로 가져다 쓸 배포 가중치가 없고, 허브에 올라온 건 얼굴 바꿔치기용이라 푸는 문제가 다르다. 쓰려면 컨테이너에 torch를 넣어야 해서 이미지가 몇 GB 불어난다.

결정 · 지우지 않고 실험적 기능으로 표시한다.

- 업로드 화면에 경고를 먼저 띄운다. 결과를 보고 나서 알려주면 늦다
- 결과에 실험적 배지와 실측 37%, 기준선 55.6%를 그대로 적는다
- "AI일 가능성이 높습니다"를 뺐다. 37%로는 그렇게 말할 수 없어서 본 것만 적는다
- 문구가 슬그머니 사라지는 게 제일 흔한 회귀라 테스트 3개로 고정했다

고려한 대안 · 기능을 지우는 것. 지우면 왜 안 되는지도 같이 사라지고, 안 되는 채로 두면 쓰는 사람을 속이는 게 된다. 그 사이에 "안 된다고 말하면서 남기는" 선택지를 골랐다.

결과 · 판단 근거로 쓰기엔 부족하지만, 얼마나 부족한지가 화면에 적혀 있다. 측정을 먼저 안 했으면 이 선택지 자체가 없었다.

## ADR-9. 논문 LLM 제공자를 DeepSeek에서 Gemini로 교체

상태: 유효

> 제공자 하나의 결제 상태로 기능이 통째로 멈추면 안 된다.

배경 · DeepSeek 잔액이 0이 되자 논문 판별이 전부 실패했다. 402 하나로 기능이 멈췄다.

트러블슈팅 6번에서 402를 친화적 문구로 바꾸는 건 이미 해뒀는데, 그건 표시 문제만 해결한 것이었다. 한 제공자에 전부 걸어둔 구조는 그대로였다.

결정 · 뉴스에서 이미 쓰던 Gemini로 옮겼다(`PAPER_MODEL = gemini-2.5-flash-lite`).

결과 · 배포에 필요한 키가 하나 줄어 설정이 단순해졌다. 다만 이제 뉴스와 논문이 같은 제공자를 쓰므로, Gemini가 죽으면 둘 다 멈춘다. 제공자 다중화는 아직 안 했다.

## ADR-10. 배포 상태를 밖에서 볼 창구를 만듦

상태: 유효

> 진단할 수단이 없으면 진단 대신 추측을 하게 된다.

배경 · 배포본을 서버 로그만 보고 진단하다 두 번 틀렸다. 한 번은 내가 넣은 코드를 범인으로 지목했는데 그 코드는 배포된 적조차 없었고, 또 한 번은 크레딧 소진 영향을 실제보다 크게 적었다.

`/health`는 프로세스가 살아있는지만, `/ready`는 DB가 붙는지만 본다. 정작 궁금한 것 — 재빌드가 새 코드를 가져왔는가, 외부 모델을 실제로 쓸 수 있는가 — 은 어느 쪽도 답하지 않는다.

결정 · `/diagnostics`를 만든다.

- 코드 지문 — 판별 동작을 정하는 파일 3개의 내용을 해싱한다. 커밋 해시를 쓰려면 빌드 인자를 넘겨야 하는데 그건 플랫폼 설정에 의존한다. 파일 내용을 직접 해싱하면 아무 설정 없이도 코드가 바뀌면 바뀐다
- 동작 설정값 — 샘플 프레임 수, 호출 타임아웃, 집계 방식, 실측 정확도. 옛 배포본은 프레임이 16장이고 새 배포본은 6장이라 값만 봐도 갈린다
- `?probe=1` — 앙상블 모델을 하나씩 찔러 지금 몇 개로 판정 중인지 알려준다. 크레딧을 쓰므로 명시했을 때만 부른다

로그인 뒤에 두지 않았다. 뭔가 잘못됐을 때 보려고 여는 곳인데 로그인을 요구하면 정작 그때 못 본다. 대신 비밀값은 안 담고 설정 여부만 참·거짓으로 준다. 값이 새지 않는지 테스트로 고정했다.

결과 · 배포 반영 여부를 20초 안에 확인할 수 있게 됐다. 실제로 이 창구와 정적 파일 해시 대조 두 가지가 같은 답을 내서, 커밋 6개가 배포에 안 걸리고 있다는 걸 추측 없이 확정했다.

## 열 건에서 반복된 것

### 개별 지점이 아니라 그 지점이 속한 계층을 바꿨다

3, 4, 5가 같은 모양이다. 라우트마다 예외를 감싸는 대신 전역 핸들러를, 호출부마다 경로를 검사하는 대신 저장 함수 하나를, 엔드포인트마다 응답을 맞추는 대신 공통 헬퍼를 뒀다. 한 군데씩 고치면 반드시 빠뜨리는 곳이 생긴다.

다만 계층을 바꿔도 그 계층의 양쪽 끝을 다 보지 않으면 소용없다. 5번에서 서버 응답 형식은 통일했는데 프론트가 그 형식을 제대로 읽는지는 안 봐서, 모든 에러가 화면에서 같은 문구로 뭉개지고 있었다.

### 재보기 전에는 되는지 안 되는지 모른다

7과 8이 그렇다. 7에서는 모델 5개를 같은 표본으로 재봤더니 정확도가 같은데 실패 방향이 반대라는 걸 알았고, 그래서 합칠 수 있었다. 8에서는 오탐 하나를 고치고 끝냈다면 여전히 안 되는 걸 된다고 믿고 있었을 것이다.

숫자를 재면 선택지가 늘어난다. 8에서 "지우기"와 "그냥 두기" 사이에 "안 된다고 말하면서 두기"를 고를 수 있었던 건 37%라는 값이 있었기 때문이다.
