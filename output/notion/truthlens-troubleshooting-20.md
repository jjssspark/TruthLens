### 20. 서버가 뭐라고 하든 화면엔 같은 문구만 떴다 — 프론트가 봉투의 반대쪽을 읽고 있었음
- 증상: 이미지 업로드가 실패하는데 화면에는 항상 "분석 요청에 실패했습니다" 한 문구만 떴다. 4장을 올리면 "서버 응답을 해석할 수 없습니다"가 떴다.
- 재현 조건: 배포본에서만. 로컬은 정상이었다.
- 원인(표면): 4장 업로드는 gunicorn 기본 타임아웃(30초)을 넘겼다. `analyze_multiple`이 순차 루프인데(`image_service.py`), HF 호출 하나가 최대 20초(`hf_deepfake_client.py`, `timeout=20`)이고 `Dockerfile`에 `--timeout` 지정이 없었다. 워커가 중단되며 응답이 JSON이 아니게 되어 `JSON.parse`가 터진 것이다.
- 원인(근본): **프론트가 실패 봉투의 반대쪽 필드를 읽고 있었다.**

  ```js
  // static/js/main.js — 고치기 전
  onError((json && json.data) || { message: '분석 요청에 실패했습니다.' });
  ```

  `backend/api/response.py`의 `fail()`은 실패 시 `data`를 **항상 `null`**로 두고 메시지를 `error`에 담는다. 그래서 `json.data`는 언제나 falsy였고, **서버가 무슨 말을 하든 기본 문구로 뭉개졌다.** 400도 500도 502도 화면에서 구분되지 않았다. 이게 진짜 문제였다 — 타임아웃은 그 뒤에 가려져 있던 증상 하나였을 뿐이다.
- 시도했지만 안 된 것 — 되돌렸다:
  - HF 호출을 병렬화하고 `--timeout 120`을 넣어 배포했다(`8138e4e`). 그랬더니 **1장짜리도 500이 되기 시작했다.** 그전까지는 최소한 결과가 나오긴 했다.
  - 의존성 드리프트를 의심했다. `requirements.txt`가 21개 전부 버전 미고정이라 재빌드 때 cv2·Pillow가 올라갔을 수 있었다. 실제 PNG로 로컬에서 판별기를 돌려 확인했고 정상이었다(`local-heuristic`, score 84.0). **아니었다.**
  - 원인을 못 좁힌 채로 두면 시연을 못 하므로 통째로 되돌렸다(`37c0658`).
  - 예고했던 "한 줄 교체" 병렬화는 애초에 불가능했다. `ImageService.analyze()`가 `flask.session`(요청 컨텍스트 바인딩)과 `db.session`(스레드 로컬)을 쓴다. 병렬로 돌릴 수 있는 건 `detector.detect()`뿐이다.
- 해결:
  1. `main.js`가 `json.error`를 읽도록 고치고, `traceId` 앞 8자를 문구 뒤에 붙였다(`34fb33a`). 화면의 오류와 서버 로그를 연결할 수 있게 됐다.
  2. 원인이 잡힐 때까지 이미지를 1장으로 제한했다. **초과분을 조용히 잘라내지 않고 `IMAGE_COUNT_EXCEEDED`로 명시적으로 거절한다.** 잘라내면 사용자는 전부 분석된 줄 안다.
  3. 500 응답 메시지에 예외 **클래스 이름만** 넣었다(`fd79665`). 배포 로그 접근이 번거로운 상황에서 `ProgrammingError`(스키마)·`OperationalError`(DB 연결)·`MemoryError`(컨테이너)·`HFInferenceError`(외부 모델)를 화면만 보고 가를 수 있다. 클래스 이름에는 내부 값도 경로도 없다. 메시지와 스택은 계속 로그에만 남는다.
- 검증: 1장 업로드 3회 연속 성공. 그전에 로컬에서 mock 없이 전 구간(`/api/v1/detect/image` → 저장 → 해시 → DB → 판별 → 결과 저장)을 실제 이미지로 돌려 **HTTP 200, score 99.6, `hf-ensemble`(모델 3개 전부 응답), 11.4초**를 확인했다. `pytest -q` 156건 통과.
- **1장 500의 근본 원인은 확정하지 못했다.** 재빌드 후 사라졌다. 코드가 아닌 건 확실하다 — 같은 코드·같은 이미지가 로컬에서 통과하기 때문이다. 배포 환경(Postgres 연결, 컨테이너 메모리, HF 콜드스타트) 중 하나로 보이나 **트레이스백을 확보하지 못해 추측이다.** 재발하면 3번에서 넣은 클래스 이름으로 바로 갈린다.
- 배운 점: **에러 표시 경로가 망가져 있으면 그 뒤의 모든 디버깅이 장님이 된다.** 이번에 시간을 가장 많이 쓴 건 원인 분석이 아니라, 서로 다른 원인들이 화면에서 전부 같은 문구로 보였다는 사실을 눈치채는 데였다. API 봉투를 정의했으면 **프론트가 그 봉투를 제대로 여는지도 같이 검증해야 한다.** 이 저장소에는 프론트엔드 테스트 러너가 없어 백엔드 테스트 156건이 전부 통과하는 동안에도 이 버그가 살아 있었다.
- 추후 관리:
  - 이미지 1장 제한은 임시다. `image_routes.MAX_IMAGES`, `templates/detect_image.html`, README 두 곳을 같이 되돌려야 한다.
  - `requirements.txt` 21개가 전부 버전 미고정이다. 재빌드마다 다른 것이 설치될 수 있어 "코드를 안 고쳤는데 깨졌다"를 판별할 수 없다.
  - 로컬 1장 11.4초다. 컨테이너에서 모델이 콜드면 30초를 넘길 수 있다. 다장 지원을 되돌릴 때 `--timeout` 상향이 같이 필요하다.
