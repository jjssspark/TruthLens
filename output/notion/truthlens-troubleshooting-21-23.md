### 21. 뉴스 판별이 실패를 성공으로 위장하고 있었음 — 구글 에러 원문이 '논리성' 칸에 표시됨
- 증상: 뉴스 분석 결과의 **논리성 항목**에 이런 문자열이 그대로 떴다.

  ```
  403 Request had insufficient authentication scopes.
  [reason: "ACCESS_TOKEN_SCOPE_INSUFFICIENT" domain: "googleapis.com"
   metadata { key: "service" value: "generativelanguage.googleapis.com" }
   metadata { key: "method" value: "google.ai.generativelanguage.v1beta.GenerativeService.GenerateContent" }]
  ```

- 재현 조건: 배포본에서만. 로컬은 정상이었다(`score=72.0`, `logic=주장의 근거가 일부 부족합니다.`).
- 원인(표면): `ACCESS_TOKEN_SCOPE_INSUFFICIENT`는 **OAuth 액세스 토큰으로 인증됐을 때만** 나오는 코드다. API 키에는 스코프라는 개념이 없어 키가 틀리면 `API_KEY_INVALID`가 뜬다. 즉 배포 환경에 `GEMINI_API_KEY`가 없어 SDK가 다른 자격증명으로 넘어간 것이다. `config.py`는 `os.getenv("GEMINI_API_KEY")`라 없으면 조용히 `None`이 된다.
- 원인(근본): **판별기가 모든 예외를 삼키고 결과를 지어내고 있었다.**

  ```python
  # news_detector.py — 고치기 전
  except Exception as e:
      message = str(e)
      ...
      "logic": message,     # ← 구글 에러 원문이 분석 결과인 척
  ```

  이것 때문에 세 가지가 연쇄로 벌어졌다.

  | | 실제 동작 | 정상 동작 |
  |---|---|---|
  | HTTP | 200 성공 | 502 `ANALYSIS_FAILED` |
  | DB | `status='done'`으로 저장 | 저장 안 함 |
  | 캐시 | `content_hash` 기준 **7일간 재사용** | 재사용 없음 |
  | 사용자 | 구글 내부 에러 원문 | "잠시 후 다시 시도해주세요" |

  `news_routes.py`에 502 분기가 **이미 있었는데 한 번도 실행되지 않았다.** 판별기가 예외를 올려보내지 않아서다.
- 6번(DeepSeek 402 원문 노출)과 같은 유형이다. 그때는 논문 쪽만 고쳤고 뉴스는 남아 있었다.
- 곁다리로 드러난 것: `test_detect_news_api_accepts_text`가 **목 없이 실제 Gemini를 호출**하고 있었다. 그런데도 늘 통과했다 — 삼킴 때문에 실패해도 200이 나왔기 때문이다. 목으로 막았다.
- 해결:
  - `NewsAnalysisError`를 두고 실패를 그대로 올린다. **`ValueError`를 쓰면 안 된다** — 라우트가 그걸 사용자 입력 오류로 보고 400 `INPUT_REQUIRED`를 반환한다. 외부 API 장애는 사용자 잘못이 아니다.
  - `NewsService`는 실패 시 요청 행을 `'failed'`로 표시하고 예외를 전파한다. 캐시 조회는 `status='done'`만 보므로 실패는 재사용되지 않는다.
- 검증: `pytest -q` 159건 통과(기존 156 + 신규 3). 배포 후 사용자 시연으로 정상 확인.
- 추후 관리: 이미 캐시된 실패 결과는 `status='done'`으로 남아 7일간 재사용된다. 같은 기사로 재시연하려면 텍스트를 바꾸거나 해당 행을 지워야 한다.
- 배운 점: **에러 처리를 "죽지 않게 하는 것"으로 이해하면 이렇게 된다.** 삼키고 기본값을 돌려주면 앱은 안 죽지만, 실패가 정상 결과로 저장되고 캐시되어 더 오래 살아남는다. 죽지 않는 것과 실패를 감추는 것은 다르다.

### 22. 논문 판별이 통째로 멈춤 — DeepSeek 잔액 0, Gemini로 교체
- 증상: 문서 분석이 전부 실패. 화면에는 "DeepSeek API 잔액이 부족합니다. API 키 결제 상태를 확인하세요."
- 재현: 로컬에서 짧은 텍스트로 API를 직접 호출해 바로 재현했다.

  ```
  Error code: 402 - {'error': {'message': 'Insufficient Balance', 'type': 'unknown_error',
   'param': None, 'code': 'invalid_request_error'}}
  ```

- 원인: 키는 유효했고(길이 35, 인증 통과) **잔액만 0이었다.** 6번에서 겪은 것과 같은 원인이 재발했다. 그때는 원문 노출을 고쳤을 뿐 의존 자체는 남겨뒀다.
- 이번에 화면 문구가 원인을 정확히 말해준 것은 20번에서 프론트 봉투 버그를 고쳤기 때문이다. 그 전이었다면 "분석 요청에 실패했습니다"로만 보였을 것이다.
- 검토한 선택지:

  | 안 | 판단 |
  |---|---|
  | DeepSeek 충전 | 코드 변경 0이지만 잔액이 또 떨어지면 같은 상황이 반복된다 |
  | 그대로 두고 문서화 | 시연에서 기능 하나가 빠진다 |
  | **Gemini로 교체** | 뉴스가 이미 쓰는 키를 재사용해 외부 결제 의존이 사라진다 |

- 해결: Gemini가 **OpenAI 호환 엔드포인트**를 제공하므로 클라이언트 설정 세 줄만 바꿨다. 프롬프트·JSON 파싱·참고문헌 제거·발췌 샘플링·인용 분석은 한 줄도 건드리지 않았다.

  | | 전 | 후 |
  |---|---|---|
  | base_url | `api.deepseek.com/v1` | `generativelanguage.googleapis.com/v1beta/openai/` |
  | model | `deepseek-chat` | `gemini-2.5-flash-lite` |
  | 키 | `DEEPSEEK_API_KEY` | `PAPER_API_KEY` → `GEMINI_API_KEY` |

  바꾸기 **전에** 호환 엔드포인트가 `response_format={"type":"json_object"}`까지 지원하는지 먼저 확인했다. 이게 안 되면 `parse_json_response`가 깨지므로 교체 자체가 무의미했다.
- 곁다리로 잡은 것 둘:
  - 홈 화면 카드 배지가 문서 분석을 `DEEPSEEK_API_KEY`로 보고 있었다. 교체 후엔 잘 도는데 "키 필요"라고 뜬다. 그 코드에 "키가 없는데 연동됨으로 보이면 거짓말이 된다"고 적어둔 주석이 있었는데 정확히 그 상황이 될 뻔했다.
  - `os.getenv("PAPER_MODEL", 기본값)`은 `.env`에 **키만 있고 값이 비면 빈 문자열을 반환해 기본값이 무시된다.** `.env.example`을 복사하는 순간 깨진다. `or`로 받도록 고쳤다. 같은 패턴이 `news_detector.py`의 `GEMINI_MODEL`에도 있으나 그 변수가 `.env`에 없어 지금은 드러나지 않는다.
- 검증: 실제 PDF(본문 11,576자)를 목 없이 판별해 요약·핵심 주장 4건·분석 범위 문구까지 정상 반환. `pytest -q` 161건 통과(기존 159 + 신규 2).
- 추후 관리: `PAPER_API_KEY`·`PAPER_API_BASE_URL`·`PAPER_MODEL` 셋을 지정하면 코드 수정 없이 다른 제공자로 되돌릴 수 있다.

### 23. 영상 분석 — 같은 증상 아래 원인이 세 번 바뀜 (타임아웃 → 메모리 → 업로드 제한)
- 증상: 영상 분석이 실패하며 "서버 응답을 해석할 수 없습니다"(JSON 파싱 실패). **로컬은 계속 정상이었다**(score 27.6, `hf-model`, 프레임 8개).
- 이 건은 원인을 세 번 갈아탔다. 매번 **화면 오버레이의 "경과 N초"** 하나로 갈렸다.

  | 경과 | 실제 원인 | 조치 |
  |---|---|---|
  | 30초 | gunicorn 기본 타임아웃 | 프레임 판정 동시 실행 + `--timeout 120` |
  | 72.4초 | 워커가 메모리로 죽음 | 프레임을 샘플링 즉시 축소 |
  | 0초 | 앞단 프록시가 100MB에서 거부 | 브라우저에서 업로드 전 차단 |

**(1) 30초 — 순차 호출**

- 원인: `_classify_with_model`이 프레임마다 HF를 순차 호출했다. 프레임당 최대 20초 왕복 × 8개면 최악 160초인데 gunicorn 기본 타임아웃은 30초다. 실측 19.6초로 로컬 맥에서 이미 한계에 붙어 있었다.
- 해결: `ThreadPoolExecutor`로 동시 실행. 이미지 앙상블에서 쓰는 패턴과 같다. **이 메서드는 `flask.session`·`db.session`을 건드리지 않아 스레드에서 안전하다** — 20번에서 이미지 서비스를 병렬화하지 못했던 이유가 정확히 그것이었다.
- 함정: `as_completed`로 받으면 완료 순서가 섞여 `frame_highlights`의 시각이 엉뚱한 프레임 것이 된다. futures를 제출 순서대로 읽어 순서를 유지하고, 테스트로 고정했다.

**(2) 72.4초 — 원본 해상도를 그대로 들고 있었음**

- 120초(gunicorn)도 60초(프록시)도 아닌 값이라 타임아웃이 아니라 워커가 죽은 것으로 봤다.
- 시간을 쪼개니 원인이 갈렸다.

  | 단계 | 시간 |
  |---|---|
  | 프레임 샘플링(cv2 seek+decode) | 7.4초 |
  | HF 모델 판정(8프레임 동시) | 6.0초 |
  | 시간적 일관성 | 0.1초 |

- 시연 영상이 **3420×1962**였다. `_sample_frames`가 이걸 원본 해상도로 15장 들고 있었다(프레임당 약 20MB = 약 300MB). 게다가 `cv2.imencode`가 원본 그대로 JPEG로 말아 HF에 올리고 있었다(프레임당 594KB × 8장). **동시 실행으로 바꾸면서 버퍼 8개가 한꺼번에 잡혀 메모리 피크가 더 올라갔다 — (1)의 조치가 (2)를 악화시켰다.**
- 프레임을 쓰는 곳은 셋뿐이고 **전부 224×224로 줄여서 본다**(픽셀 휴리스틱, 시간적 일관성, 딥페이크 모델). 원본을 유지할 이유가 없어 샘플링 직후 긴 변 640으로 줄인다. 이미 작은 프레임은 늘리지 않는다.

  | | 전 | 후 |
  |---|---|---|
  | 전송량(1장) | 594KB | 40KB |
  | HF 판정 | 6.0초 | 1.2초 |
  | 전체 | 13.3초 | 6.1초 |
  | 프레임 메모리 | 약 300MB | 10.1MB |

- **score가 27.6 → 30.1로 2.5 움직였다.** `INTER_AREA` 리샘플링이 픽셀 통계를 조금 바꾼 것이다. 판정 구분선(60%)과 결과 문구는 그대로지만 값이 바뀐 것은 사실이다. 축소하지 않으면 컨테이너에서 아예 결과가 나오지 않으므로 감수했다.

**(3) 0초 — 요청이 앱에 닿지도 않았음**

- 경과 0초는 타임아웃일 수 없다. 배포본에 크기별로 실제 POST를 보내 경계를 찾았다.

  ```
    1MB -> 302 (앱 도달, 로그인 리다이렉트)
   50MB -> 302
   96MB -> 302
  100MB -> 413 Request Entity Too Large   (0.053초)
  113MB -> 413
  ```

- 앞단 프록시의 `client_max_body_size`가 100MB다. **시연 영상이 113MB라 매번 여기 걸렸다.** 그 413은 nginx가 만든 HTML이라 JSON 파싱이 실패했고, 화면에는 원인이 전혀 드러나지 않는 문구만 떴다.
- **앱의 `MAX_CONTENT_LENGTH`(500MB)를 조정해도 소용없다.** 프록시가 앞에 있어 요청이 앱까지 오지 않는다. 서버에서 잡을 방법이 없으므로 브라우저에서 올리기 전에 막고 파일 크기와 이유를 함께 보여준다.
- 함정: 파일 선택과 드래그앤드롭이 **각각 따로** `selectedFile`을 건드리고 있었다. 한쪽만 고치면 드롭으로 올릴 때 그대로 새어나간다. 검사를 `acceptFile` 한 곳으로 모았다.
- 안내 문구 "최대 500MB"를 "최대 96MB"로 고쳤다. README와 라우트 docstring에는 PRD 설계값(500MB)과 배포 제한(96MB)을 함께 밝혔다.
- 검증: `pytest -q` 165건 통과(기존 161 + 신규 4). 다만 **프론트엔드 테스트 러너가 없어 업로드 크기 검사는 자동 검증되지 않는다.**
- 배운 점: **"서버 응답을 해석할 수 없습니다"는 원인을 하나도 알려주지 않는다.** 세 번 다 같은 문구였는데 원인은 전혀 달랐다. 갈라준 것은 오직 경과 시간이었다 — 30초는 설정값, 72.4초는 아무 설정과도 안 맞는 값(그래서 죽은 것), 0.053초는 애초에 서버에 닿지 않았다는 뜻이었다. **어중간한 숫자는 그 자체가 단서다.**
- 추후 관리 (다음 과제로 남김):
  - **판정이 부정확하다.** 딥페이크 탐지 모델(`prithivMLmods/deepfake-detector-model-v1`)은 얼굴 조작 여부를 보는 것이라 "AI가 통째로 생성한 영상"과는 다른 문제를 푼다. 이미지 쪽에서 15번·19번을 거쳐 앙상블로 해결한 것과 같은 검토가 필요하다.
  - **여전히 느리다.** 6.1초 중 5.5초가 프레임 샘플링이다. seek과 디코딩은 원본 해상도로 할 수밖에 없어(축소는 디코딩 *후*) `MAX_SAMPLED_FRAMES`(16)를 낮추는 것 말고는 방법이 마땅치 않다.
  - 113MB 영상은 지금 구조로 업로드할 수 없다. 시연용 클립을 짧게·낮은 해상도로 따로 만들어 두는 편이 낫다.
